## 3. Schema mapping

Full mapping in `schema.sql` (delivered alongside this report). Summary of
every substantive decision:

| SQLite | PostgreSQL | Why |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | "BY DEFAULT" (not "ALWAYS") lets the migration insert the *exact* existing ids, preserving every foreign key; sequences are fast-forwarded with `setval()` after load. |
| `TEXT ... CHECK(col IN (...))` | unchanged (`TEXT ... CHECK(...)`) | Deliberately not a native Postgres `ENUM`. `db.js` already shows this project's status ladder growing twice, and each time SQLite needed a full table-rebuild workaround because it can't `ALTER` a `CHECK` in place. Postgres *can* alter a `CHECK` directly — keeping `TEXT+CHECK` gets the same future flexibility with a simpler migration path than `ENUM` (which needs `ALTER TYPE ... ADD VALUE`, can't run in the same transaction as other DDL pre-PG12, and can never remove a value). |
| `TEXT NOT NULL DEFAULT (datetime('now'))` | `TIMESTAMPTZ NOT NULL DEFAULT now()` | See Section 5 — this is a real, tracked application-code dependency, not a free change. |
| `*_json` TEXT columns (`options_json`, `parts_json`, `answers_json`, `draft_answers_json`, `locked_answers_json`, `details_json`) | kept as `TEXT` | Every one is read with `JSON.parse()`/written with `JSON.stringify()` in app code; none is ever queried by SQL today (`grep` found zero `json_extract` calls). Converting to `JSONB` would be safe and purely additive later, but isn't required for behavioral parity, so it's deliberately deferred rather than bundled into this migration. |
| Foreign keys | unchanged, with one structural exception | See Section 4. |

### Finding: a genuine circular foreign key (`tests` ↔ `attempts`)

`tests.improves_attempt_id` references `attempts(id)`, while every `attempts`
row references `tests(id)` via the `NOT NULL` `attempts.test_id`. SQLite
never surfaced this as a problem because it validates foreign keys
per-statement, not per-table-definition, so the two `CREATE TABLE`
statements can be written in either order. **PostgreSQL validates a
`REFERENCES` target at `CREATE TABLE` time**, so the two halves of this real
cycle cannot both be declared inline no matter which table is written first.

Resolution used in `schema.sql` (and proven working in the test run below):
create `attempts` first without its `test_id` foreign key inline, create
`tests` (whose `improves_attempt_id` FK can now point at the already-existing
`attempts` table, marked `DEFERRABLE INITIALLY DEFERRED`), then add
`attempts.test_id`'s foreign key via `ALTER TABLE` once `tests` exists, also
marked deferrable. The bulk loader wraps the whole load in one transaction
with `SET CONSTRAINTS ALL DEFERRED`, so neither direction of the cycle can
fail mid-load regardless of per-table insert order — every constraint is
checked once, correctly, at `COMMIT`.

This is exactly the kind of thing item 7 of the brief ("foreign
keys/indexes/constraints") was asking to be checked for, and it would not
have been found by reading the schema alone — it only became visible when
trying to actually create it in PostgreSQL.

## 4. Migration ordering & data movement

Load order used (and tested): `users → subjects → chapters → source_files →
source_documents → source_document_files → questions → visual_assets →
duplicate_flags → tests → test_questions → attempts → subscriptions →
audit_log`. With `SET CONSTRAINTS ALL DEFERRED` active for the whole
transaction, this order satisfies every foreign key except the
`tests`/`attempts` cycle, which is resolved by deferral regardless of order.

**How each specific piece of state maps across:**

- **4,946 questions** (all columns, including `options_json`/`parts_json`
  verbatim as TEXT) — migrate as one table, id-preserving. See Section 6 for
  the one real exception found.
- **Attempts/tests/subscriptions/audit_log** (real user/product data) —
  migrate as-is; no shape changes. `attempts.answers_json`,
  `draft_answers_json`, and `locked_answers_json` are copied verbatim as TEXT
  — their meaning (raw audit copy vs. the actual scored source of truth,
  vs. the immediate-feedback lock) is entirely an application-code
  convention (see `scoring.js`), not a database-level guarantee, so the
  migration doesn't need to and doesn't interpret them.
- **`locked_answers_json` / `feedback_mode` / `improves_attempt_id`** — plain
  columns, migrated like any other; `improves_attempt_id`'s only special
  handling is the deferred-FK mechanism in Section 3, not its data.
- **Source-document/visual-asset provenance** (`source_files`,
  `source_documents`, `source_document_files`, `visual_assets`) — migrated
  as relational data only; the actual PDF/image bytes they point at
  (`archive_path`) are **not** part of this migration at all and are
  untouched — `source_library/` stays exactly where Phase 2 left it, per the
  standing instruction not to clean that up yet.

## 5. Timestamp handling — a real, tracked application-code dependency

SQLite stores `datetime('now')` as naive UTC text
(`"2026-09-23 06:37:28"`, no `T`, no zone). `server.js`'s submit handler
already has to work around this by hand:
```js
const startedAt = new Date(attempt.started_at.replace(' ', 'T') + 'Z');
```
The mapped schema uses `TIMESTAMPTZ` (Section 3), which is the right target —
native comparisons, native `now()`, no more manual string surgery — but
getting there means:

1. The migration script converts every historical value using the same UTC
   assumption `server.js` already makes (proven identical for every row in
   the test run — see Section 7).
2. **At cutover (Phase 4, not this phase):** the `pg` driver returns
   `TIMESTAMPTZ` columns as native JS `Date` objects already, so
   `server.js`'s manual `.replace(' ', 'T') + 'Z'` line becomes unnecessary
   and must be removed — leaving it in would double-convert and break. This
   is flagged here as a known required code change, not made now.
3. Every raw `datetime('now')` used inside an `UPDATE`/`INSERT` statement
   (found in `server.js` three times — the autosave, check, and submit
   endpoints — and in `db.js`'s schema defaults) becomes `now()`.

## 6. Content-integrity finding: 122 `questions.correct` values are not integers — REPORTED, NOT FIXED

Running the real migration against the full preserved copy (not a synthetic
sample) surfaced a genuine, pre-existing data-quality issue that SQLite's
dynamic typing has been silently absorbing:

- **122 rows** in `questions` have a `correct` value that cannot be
  represented as the `INTEGER` the mapped PostgreSQL schema (correctly)
  requires. SQLite's column-type *affinity* system never rejects a write
  like this — it stored the text anyway.
- **Every one of the 122** comes from the same single source batch:
  `competency.pdf (Competency Focused Questions) + competency_answer.pdf`.
- **119 of the 122** hold an answer-key letter in parenthesis form (e.g.
  `"(b)"`, `"(a)"`) instead of the 0-based numeric option index every other
  MCQ row in the bank uses — apparently never converted at ingestion time.
- **The other 3** hold free-text fragments (`"decreases / nuclear charge"`,
  `"oxidising"`, `"non-metals / high"`) that aren't an option index at all —
  these look like short-answer content that was tagged `kind='mcq'` instead
  of `kind='open'`, not merely a formatting slip.
- **All 122 are `status = 'transcribed'`** — outside `GRADABLE_STATUSES`
  (`content-rules.js`), meaning **zero** of them have ever been servable in a
  scored test or practice set. This is a real, contained gap, not a
  live-scoring risk.

**What this phase did about it:** the test migration script validates every
`INTEGER`-mapped column before insertion and **excludes** a row that fails
validation rather than guessing a fix (e.g. inventing `"(b)" → 1`, which
would be a content/answer-key decision, made silently, by a migration
script — exactly what this project's standing rule against auto-fixing a
content-integrity discrepancy exists to prevent). Every excluded row is
recorded with its id, column, and raw value in `migrate-report.json`. The
automated comparison in Section 7 explicitly accounts for these 122 rows as
a *known, reported* exclusion — it does not silently ignore them.

**What this phase is explicitly NOT recommending or doing:** deciding how to
convert these 119+3 rows, promoting their status, or touching the live
database. That is a content decision for the same review process as any
other question in the bank, on the same standing terms as everything else in
this project's source-of-truth rules — not something to be resolved as a
side effect of an infrastructure migration. It is flagged here so it's a
known, tracked item before Phase 4, not a surprise discovered mid-cutover.

## 8. Query-compatibility findings (real, found by running actual app queries against both engines)

Running one of `server.js`'s real endpoint queries (`/api/content/summary`'s
aggregate) against both engines side-by-side surfaced two concrete
`node:sqlite`-vs-`pg` driver differences that are easy to miss by reading
code alone:

1. **Column-alias casing.** SQLite returns a query's column names exactly as
   written (`subjectCount`, `chapterCount`). PostgreSQL folds every
   *unquoted* identifier — including `SELECT ... AS aliasName` — to
   lowercase, so the exact same query returns `subjectcount`, `chaptercount`
   from the `pg` driver. `server.js`'s handler destructures results as
   `r.subjectCount` — **this will silently read `undefined` under
   PostgreSQL** unless every camelCase alias in every query is either
   double-quoted (`AS "subjectCount"`) or the JS is updated to read the
   lowercase key. This affects every query in `server.js`/`practice.js`/
   `diagnostics.js`/`readiness.js` that uses a camelCase `AS` alias.
2. **`COUNT(...)` returns a string, not a number.** PostgreSQL's `COUNT()`
   is a `bigint`, and the `pg` driver deliberately returns `bigint` values as
   JS strings (to avoid silent precision loss above 2^53). SQLite returns a
   plain JS number. `server.js`'s summary handler does
   `acc.subjects + r.subjectCount` — under PostgreSQL this becomes **string
   concatenation, not addition**, a real, silent correctness bug if the
   driver swap happened without this being caught. Fix is either an
   explicit `::int` cast in the SQL or `Number(...)` at the call site —
   needs to be applied everywhere an aggregate result feeds arithmetic.

Both are exactly the class of item 3 ("queries needing compatibility
changes") the brief asked to identify, and both were only found by actually
running a real query against both engines and diffing the JS-level result
shape — not visible from reading the SQL text alone.

## 9. Code-level changes required at cutover (Phase 4) — not made in this phase

Cataloged here as design output; none of these were touched:

- **Placeholder syntax:** SQLite's positional `?` vs. `pg`'s `$1, $2, ...`
  appears at roughly 40+ call sites across `server.js`, `practice.js`,
  `diagnostics.js`, `readiness.js`, `content-rules.js`, `ingest.js`.
  Recommend a small compatibility shim that accepts the existing `?`-style
  call sites and translates positionally, rather than hand-rewriting every
  query — lower risk, smaller diff, easier to review.
- **Sync → async:** `node:sqlite`'s `DatabaseSync` is fully synchronous
  (`.get()/.all()/.run()` return immediately); `pg` is promise-based. Every
  currently-synchronous DB-touching function (`hasActiveAccess`,
  `loadQuestionsForTest`, `logEvent` in `server.js`; every exported function
  in `practice.js`, `diagnostics.js`, `readiness.js`, `retest.js` reads
  synchronously via `diagnostics.js`; `ingest.js`) becomes `async`, and every
  caller needs an `await`. `server.js`'s route handlers are already `async`
  (they already `await readBody`), so this is mechanical but touches most of
  the codebase — by far the largest single code change at cutover, and the
  reason this project's own 12–15 working day estimate treats Phase 4 as
  multi-day, not a single afternoon.
- **`lastInsertRowid` → `RETURNING id`:** every `db.prepare(...).run(...)`
  that currently reads `info.lastInsertRowid` (in `server.js`, `practice.js`,
  `ingest.js`) needs its `INSERT` to add `RETURNING id`, since `pg` has no
  equivalent auto-property.
- **`INSERT OR IGNORE`** (`ingest.js`, `source_document_files`) → `INSERT ...
  ON CONFLICT DO NOTHING` (the table's existing composite primary key
  already provides the conflict target — no schema change needed for this
  one, confirmed while writing `schema.sql`).
- **`PRAGMA table_info(x)`** (used at every startup for `db.js`'s additive
  migrations) → `information_schema.columns` query. Note: PostgreSQL's
  native `ALTER TABLE ... ADD CONSTRAINT` also means the two CHECK-widening
  *table-rebuild* blocks in `db.js` (the "SQLite can't ALTER a CHECK in
  place" workaround) have no PostgreSQL equivalent needed at all — that
  entire pattern goes away, it isn't ported.
- **Two query-result findings from Section 8** (alias casing, bigint-as-
  string) apply everywhere a query result is read by property name or used
  in arithmetic.
- **Timestamp parsing** (Section 5) — remove the manual
  `.replace(' ','T')+'Z'` once the driver returns real `Date` objects.

## 10. Connection pooling, transaction boundaries, concurrency & rollback (design)

- **Pooling:** a single `pg.Pool` per process, sized modestly to start (the
  Phase 9 audit found no existing load data to size against — recommend
  starting conservative, e.g. 10 connections, and measuring under the Phase
  7 concurrency test before raising it). Route handlers use
  `pool.query(...)` for single statements.
- **Transactions:** anywhere the code currently does manual
  `db.exec('BEGIN TRANSACTION')`/`COMMIT`/`ROLLBACK` (today: `ingest.js`'s
  batch insert, and `db.js`'s own migration blocks, which won't be ported —
  see Section 9) must check out **one dedicated client** from the pool for
  the whole transaction (`pool.connect()` → `client.query('BEGIN')` → ... →
  `COMMIT`/`ROLLBACK` → `client.release()`), never call `pool.query()`
  mid-transaction, since the pool can hand different statements to different
  physical connections. This is a real behavior change from `node:sqlite`'s
  single-connection model, where this risk doesn't exist.
- **Concurrency safety:** this is where PostgreSQL is a genuine improvement,
  not just a lateral move — `DatabaseSync` is a single blocking connection
  today (confirmed in the Phase 9 audit), so concurrent requests already
  serialize on it; a pool allows real concurrent reads and writes. The
  specific risk to design for before Phase 7's concurrency test:
  `/api/attempts/:id/check` and `/api/attempts/:id/answers` both
  read-modify-write the same `attempts` row (`locked_answers_json`,
  `draft_answers_json`) — under real concurrency this needs either a
  transaction with `SELECT ... FOR UPDATE` on that row, or an atomic
  `UPDATE ... SET locked_answers_json = jsonb_set(...)`-style single
  statement, to avoid a lost-update race between two rapid requests for the
  same attempt. Not an issue today only because `DatabaseSync` serializes
  everything by accident, not by design.
- **Rollback strategy:** the live SQLite database is the disaster-recovery
  fallback for the entire duration of the migration project, exactly as
  instructed — nothing about Phase 3 or Phase 4 removes or disables it. If
  a PostgreSQL cutover needs to be reversed, the app's `db.js` require
  simply points back at `node:sqlite`/the untouched `boardready.db` file,
  which this phase has confirmed is still byte-identical to its pre-Phase-3
  state.
