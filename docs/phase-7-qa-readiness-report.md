## 2. Tests and tools created

- **`scripts/stage7-load-test.js`** — a progressive concurrency harness that ramps 10 → 25 → 50 → 100 → 200 simulated students, stopping early if a tier breaches a launch-blocker threshold. Per tier it measures response-time percentiles (p50/p95/p99) per endpoint, error/timeout counts, failed and duplicate submissions, lost autosaves, cross-user contamination, and database errors — exactly your list. Authenticates each simulated user once and reuses their token, specifically to avoid re-tripping the login rate limiter on every request (see point 5).
- **`scripts/stage7-browser-matrix-check.js`** — extended device/browser QA covering Desktop, Tablet (iPad Pro 11), Mobile (iPhone 13), and Mobile under simulated Slow 3G, plus four standalone behavioral checks: browser back-button, session expiration, autosave/resume, and a forced backend-error state. Both scripts are committed at `fa9cde9`→`1cae5aa` (Phase 7 commit) with the QA plan.

Both were debugged iteratively against a **disposable copy** of the live database (never the live file itself — hash `cda008e972b4caf5453537cc33f52e473300ad225bf5d384aef3399009d18c52`, re-verified unchanged after every run), the same pattern used throughout this project. Three real bugs in the harness itself were found and fixed before trusting its output: a shared-browser-context login leak that made three of the four behavioral checks silently run already-authenticated instead of from a clean login screen; a race condition checking for immediate-feedback CSS classes before the server's `/check` response had actually returned; and a wrong test assumption that "autosave" meant Practice mode's answer-picking, when the code shows Practice persists resumable answers through `/check`'s own transaction — the debounced `PATCH /answers` autosave path only Board Simulation (deferred) mode actually uses. All three were harness defects, not product defects, and are now fixed.

## 3. What was verified locally

**Load/concurrency harness**, run against both engines on disposable local databases:
- **PostgreSQL**: clean at every tier — **10, 25, 50, 100, and 200 concurrent users** — zero errors, zero timeouts, zero failed/duplicate submissions, zero lost autosaves, zero cross-user contamination, at every tier including 200. p95 response times at 200 users: `/submit` 449ms, `/check` and `PATCH /answers` 1414ms, `/practice/generate` 692ms — within or close to the plan's own thresholds even at the top tier, which isn't a required pass/fail gate above 100 users.
- **SQLite**: a genuine, reproducible **lost autosave at tier 10** (not a harness artifact — confirmed via a controlled fix-and-retest cycle that ruled out two harness bugs first: silently-swallowed promise rejections, and unretried "database is locked" errors from the harness's own bookkeeping reads racing the server process on the same file). Root cause: `db-sqlite.js`'s `transaction()` has no serialization across concurrent requests sharing the one `DatabaseSync` connection, unlike Postgres where each transaction checks out its own pooled connection with real isolation plus `SELECT ... FOR UPDATE`. **This is SQLite-only and does not affect the Postgres staging/production target** — reported here, not fixed, per the "report every issue before fixing" discipline you set for this stage.

**Browser/device matrix**, final clean run: Desktop, Tablet, and Mobile (iPhone 13, normal network) all passed with **zero findings, zero CSP violations, zero page errors**. Two items did not pass and are reported below rather than silently fixed:

- **Mobile under simulated Slow 3G timed out** waiting for the test screen to appear (45s budget) when run as the fourth sequential profile in one continuous test session. An isolated run of the *identical* flow (fresh browser process, nothing run before it) completed the same steps in **~8.3 seconds** — confirmed twice. This strongly suggests a **local-sandbox artifact**: the headless browser and the server-under-test share this sandbox's CPU, and three back-to-back full end-to-end walkthroughs (each including real password hashing, two full test attempts, and DOM-heavy interaction) ahead of it appear to create contention that a real deployment wouldn't have, since Railway's server and this test tooling's browser would run on separate machines. I was not able to fully isolate the exact mechanism within this session's remaining verification time — it's flagged honestly as needing re-confirmation once this tool runs against real staging, not swept aside.
- **Browser back-button test**: reproducible, confirmed by reading `public/app.js`. The app is a single-page app that never calls `history.pushState` for its own screen transitions (dashboard/test/results are all shown and hidden within one document load) — so pressing the browser's actual Back button doesn't move to a previous in-app screen, it navigates the tab away from the app entirely. This is a real product gap, not a harness bug, but it's a UX/product decision, not a correctness or security defect — not fixed here, since Stage 7 is explicitly not a product-change stage.
- **Session-expiration test**: reproducible, and I traced the exact cause in `public/app.js`. `enterApp()` calls `showScreen('dash')` *before* `await refreshDashboard()` resolves, and every one of `refreshDashboard()`'s sub-fetches (subjects, readiness, summary, recent attempts) independently catches its own error and just shows a toast — none of them call `clearSession()` or redirect to login on a 401. Net effect: **an expired or invalid token leaves the student stranded on a broken, mostly-empty dashboard with error toasts, instead of being bounced cleanly to the login screen.** This is a genuine, confirmed application bug (not a harness assumption problem, unlike the autosave one) — reported here for you to schedule, not fixed in this pass.

Both the SQLite lost-autosave finding and this session-expiration finding are real defects; neither was touched, per your explicit "report every issue before making any fixes" instruction for this stage.

Full test suite: **38/38 passing** on both engines after all of this. Live SQLite database hash unchanged throughout.

## 5. Pass/fail thresholds (from the plan)

Launch blockers (0 tolerance, at or below the 100-user tier): duplicate submissions, lost autosaves, cross-user contamination, answer-key leakage, authorization bypass, and any live-database/preserved-master modification. Performance gates: 5xx rate < 1% at ≤100 users; p95 `/check` and `PATCH /answers` < 500ms at ≤50 users / < 1500ms at 100; p95 `/submit` < 1000ms at ≤50 / < 2500ms at 100; p95 `/practice/generate` < 800ms at ≤50 / < 2000ms at 100; zero database connection errors at ≤100 users; zero CSP violations and zero uncaught exceptions at every device/network combination. Anything above the 100-user tier is explicit capacity discovery, not a pass/fail gate — Railway's staging tier is unlikely to be sized for 200 concurrent users, and the point of ramping is to find the real ceiling honestly.

## 6. Risks, assumptions, and open questions

- **Open question, not decided on your behalf** (Section 4 of the plan): authenticating 100–200 real staging users through the real login endpoint will take multiple 15-minute windows at the rate limiter's 10-attempts-per-15-minutes cap, regardless of how many concurrent users are being simulated. Three options for you to choose once staging exists: (a) spread the load test's login phase across several 15-minute windows, (b) temporarily raise the login rate limit via an environment-configurable override for the staging test window (a small, clearly-flagged change, not silently made), or (c) accept a lower top tier reachable within one window. This plan intentionally does not pick one.
- **SQLite lost-autosave finding** is real but out of scope for the Postgres staging/production path — flagged for awareness, not urgency, unless SQLite is ever used for anything beyond local dev/tests.
- **Session-expiration bug** (stuck dashboard on an expired token) is a genuine, real, currently-unscheduled defect. It doesn't touch any of the launch-blocker correctness/security invariants (no data leaks or cross-user exposure), but it is a real, confirmed user-facing bug worth deciding when to fix.
- **Back-button behavior** is a product/UX decision (whether to add SPA history management), not a defect — flagged for your backlog, not treated as a QA failure.
- **Slow-3G timing anomaly** is the one item I couldn't fully close out locally — most likely a sandbox artifact from browser/server CPU sharing, not a real capacity limit, but not proven either way without re-running against real, separately-hosted staging infrastructure.
