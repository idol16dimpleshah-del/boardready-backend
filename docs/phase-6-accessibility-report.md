# Phase 6 — Accessibility pass

**Date:** 2026-09-22
**Scope:** the first item in your explicitly confirmed next-phase order — "1. Accessibility pass ↓ 2. Full mobile QA ↓ 3. Diagram extraction + association ↓ 4. Final visual polish." No new features, no visual redesign: this makes the existing Practice / Board Simulation / Improve My Score flow usable by keyboard, screen reader, and low-vision students, without changing what any of those screens look like at a glance.

## Method

An audit first, then fixes, then two independent verification passes — automated (axe-core, the industry-standard WCAG rule engine, run against the real live pages, not a static analysis of the source) and manual (a real keyboard-only walkthrough of the exact interactions a student without a mouse would need). Both are real, repeatable scripts against the running app, not descriptions of what should work.

## What was found and fixed

**Keyboard access — the question navigator (WCAG 2.1.1, Level A).** The strip of dots a student uses to jump between questions was a plain `<div>` with only a mouse click handler. A keyboard-only student could not reach it at all — not focus it, not activate it. It's now a real `<button>` per question, with a descriptive `aria-label` ("Question 3, answered, flagged for review") replacing what was previously color-only information, and `aria-current="true"` on whichever question is open.

**Keyboard access — the diagram zoom (WCAG 2.1.1, Level A).** Same bug, different element: the "tap to zoom" diagram thumbnail was a `<div>` with a mouse-only `onclick`. It now has `role="button" tabindex="0"` and a real `aria-label`, plus an Enter/Space keydown handler doing what the click handler already did.

**Modal semantics and focus management (WCAG 2.4.3, 4.1.2).** The diagram lightbox had no dialog role, never moved focus when it opened, never gave focus back when it closed, and had no Escape key to close it — meaning once a keyboard user got trapped in a page behind the (invisible-to-them) lightbox, there was no way out except reloading. It's fixed properly, not partially: `role="dialog" aria-modal="true" aria-label="Zoomed diagram"`; opening it moves focus to the close button; closing it (via Escape, the close button, or a click on the backdrop) returns focus to the exact diagram trigger that opened it, and the Escape listener is removed again so it doesn't leak into the rest of the page.

**Color contrast (WCAG 1.4.3, Level AA).** A real per-token audit (the actual WCAG relative-luminance formula, not a guess) found `--ink-faint` (secondary text — labels, meta text, timestamps) and four status colors (`--success`, `--warning`, `--critical`, `--cyan`) measuring 3.1–3.8:1 against white, below the 4.5:1 AA minimum for normal-weight text at the sizes they're actually used at. All five were retuned a fraction darker, same hue, clearing 4.5:1 — a token-level fix that corrects roughly 25+ downstream usages without touching any component's markup. A second, independent axe-core scan then caught what the first hand-computed pass missed: three real spots (`.tabrow`, `.chapter-row`, the answer-feedback banners) composite `--ink-faint` over a translucent tinted background rather than pure white, which measured 4.06–4.31:1 — still short. `--ink-faint` was darkened again (`#797099` → `#6D658A` in light mode, `#827C9E` → `#918CAA` in dark mode, both checked against every real background the token is used against, not just the easy case) and a follow-up scan confirmed zero contrast violations left, in both themes.

**Missing document language (WCAG 3.1.1, Level A).** `<html>` had no `lang` attribute — added `lang="en"`.

**Form labels and autofill (WCAG 1.3.1, 4.1.2).** Login and account-creation fields were visually labeled but not programmatically associated — a screen reader announced them as unlabeled edit fields. Added real `<label for="…">`/`id` pairs plus `autocomplete` hints (`email`, `current-password`, `new-password`, `name`) so password managers and browser autofill work correctly too.

**Toggle and state information that was color-only (WCAG 1.4.1, 4.1.2).** The board/subject filter chips, the flag-for-review button, and the locked MCQ options (correct/incorrect/selected) all communicated their state purely through color and an icon. A colorblind or screen-reader user got none of that. Toggle chips now carry real `aria-pressed`; locked options carry hidden text like "(your answer — correct)" alongside the icon (now marked `aria-hidden` since it's decorative once the text exists); all 13 static SVGs in the page (logos, icons already paired with visible text) got `aria-hidden="true"` so a screen reader doesn't read out meaningless graphic descriptions.

**Live announcements (WCAG 4.1.3).** Moving between questions is a fully client-side re-render — nothing told a screen-reader user that the question actually changed. Added one `aria-live="polite"` region that announces "Question 3 of 12" (plus ", flagged for review" when relevant) on every navigation. The exam timer deliberately does *not* get this treatment — an early draft would have announced the time out loud once a second, which is spam, not an accommodation. It's now a real `role="timer"` element with a static, screen-reader-only "Time remaining:" label and a separately-updating value span, so the actual time is always in the accessibility tree without being read aloud every tick.

**Touch target size (WCAG 2.5.8).** The question-navigator dots were 11px, well under the 24×24px minimum. Given the constraint you set — no redesign — this was treated honestly rather than silently left alone or over-corrected: each dot's actual clickable/tappable button box grew to 20px (24px for the current question), with the *visual* dot inside it staying close to its original size via a pseudo-element, so the row doesn't visually change but the real target got measurably bigger. This is a partial improvement, documented as such — a fully compliant 24px row of ten-plus dots would need more horizontal space than the current design allows, which is exactly the kind of layout change you asked to defer to the final visual-polish phase.

**Already compliant, no fix needed (confirmed, not assumed):** `prefers-reduced-motion` was already handled by one global rule covering every animation/transition in the app. A `:focus-visible` outline was already present almost everywhere; the one exception (login form inputs, which use a box-shadow ring instead of the default outline) was judged an acceptable alternative indicator, not a failure.
