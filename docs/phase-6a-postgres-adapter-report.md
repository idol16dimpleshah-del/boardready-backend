# Phase 6A — PostgreSQL Application Adapter: Completion Report

**Date:** 2026-09-24
**Scope:** exactly Stage 6A from `docs/phase-6-postgres-cutover-plan.md` — replace `node:sqlite`'s synchronous DB access with a genuine PostgreSQL-compatible async path, without deleting or degrading the existing SQLite path, and without touching the live database, the source library, or any question's `status`/`answer_status`.

---

## What was built

**`db.js` split into a three-file dual-engine design**, selected by `DB_ENGINE=sqlite|postgres` (default `sqlite`, so every existing deployment/script/test that never sets this env var is completely unaffected):

- **`db.js`** — a ~20-line dispatcher. Computes the shared test-mode detection once and requires whichever engine module `DB_ENGINE` names.
- **`db-sqlite.js`** — the entire previous `db.js` content (schema, additive migrations, the file-path-based test-isolation guard), byte-for-byte unchanged in behavior, wrapped in a factory function and given the new shared method shape. Its `.prepare(sql).get/.all/.run()` are still **plain synchronous functions returning real values, not Promises** — this is what keeps every one of the ~90 one-off `archive-*`/`ingest-*`/`backfill-*`/`reclassify-*`/`fix-*` scripts, plus `seed.js`, `debug-dup.js`, and `audit-publication-readiness.js` (none of which this phase touches, per "never re-ingest completed sources") working with **zero code changes**, since they never `await` these calls.
- **`db-postgres.js`** (new) — a `pg.Pool`-backed adapter exposing the identical `db.prepare(sql).get/.all/.run()` shape, but real `async`/`Promise`-returning. Translates `?` placeholders to `$1..$n`, and reads a generated id back into `lastInsertRowid` when the SQL text itself contains `RETURNING` (see below). Does **not** run any schema DDL itself — it assumes the target database was already provisioned via the existing `docs/phase-3-migration-artifacts/schema.sql` + `migrate.js`, matching how a real production Postgres deployment actually manages migrations (a deliberate, separate step, never an implicit side effect of the app booting).

**Shared surface both engines expose:** `db.prepare(sql).get/.all/.run(...)`, `db.transaction(async (txDb) => {...})`, `db.ENGINE` (`'sqlite'|'postgres'`), `db.NOW_SQL` (`"datetime('now')"` vs `'now()'`), `db.ready()` (async connectivity check), `db.DB_PATH`/`db.LIVE_DB_PATH`/`db.IS_TEST_MODE` (unchanged reporting fields).

**The "mechanical `await`, no branching" design actually held.** Because SQLite's methods stay synchronous, `await db.prepare(sql).get(x)` is correct and safe under *either* engine — `await` on a plain value just resolves it on the next microtask. Every one of the 51 originally-inventoried call sites across `server.js`, `practice.js`, `readiness.js`, `diagnostics.js`, and `content-rules.js` now uses this exact pattern; none needed an engine-specific branch.

## Genuine cross-engine fixes made (not just `await` insertion)

1. **`RETURNING id` added explicitly** to the 4 SQL statements that previously relied on `node:sqlite`'s `lastInsertRowid`: `server.js`'s `register()` (users insert) and the attempts insert, and `practice.js`'s two `tests` inserts (`generate()` and `generateImprovementTest()`). Verified `node:sqlite` itself supports `RETURNING` (confirmed empirically before relying on it) — so this one shared SQL text works for both engines, with each engine's wrapper reading the returned row's `id` back into `lastInsertRowid`.
2. **Camel-case SQL aliases double-quoted** at every site found in the Phase 6 planning audit — Postgres silently lowercase-folds an unquoted mixed-case alias, which would have broken every `r.subjectId`/`r.testId`/etc. read in the app: `server.js`'s `/api/content/summary` and `/api/attempts/me` (15 aliases, the most in the app), `diagnostics.js`'s `getStudentStepHistory`, and `readiness.js`'s `speedComponent`. Quoting is a no-op under SQLite and the real fix for Postgres — one shared SQL string for both engines.
3. **`COUNT()` bigint-string coercion.** Postgres's `pg` driver returns a `COUNT()` as a JS string (to avoid precision loss past `Number.MAX_SAFE_INTEGER`). Fixed with explicit `Number(...)` at the three affected call sites: `/api/content/summary`'s three counts, and `readiness.js`'s `syllabusCoverageComponent` (`totalChapters`, `totalBandsInBank`). The `totalBandsInBank` fix also closes a subtler latent bug found during the Phase 6 audit: the existing `... || 1` fallback would never have fired once `n` was a string, since `Number("0")` is falsy but the string `"0"` itself is truthy.
4. **Timestamp handling.** `server.js`'s inline `attempt.started_at.replace(' ', 'T') + 'Z'` (a SQLite-TEXT-specific hack) is replaced with a small `parseDbTimestamp()` helper that accepts either a SQLite TEXT string or a real JS `Date` (what Postgres's `TIMESTAMPTZ` columns come back as via the `pg` driver). The three inline `datetime('now')` SQL fragments (draft/lock saves in `/answers` and `/check`, `submitted_at` in `/submit`) now use `db.NOW_SQL`, resolving to `datetime('now')` or `now()` per engine.
5. **Postgres-specific test-database isolation guard**, mirroring `db-sqlite.js`'s file-path-based one but connection-string/database-name based: refuses to run in test mode without an explicit `DATABASE_URL`, and denylists the literal names `boardready`/`boardready_production`/`boardready_staging` as a test target — the same "explicit but wrong is just as unsafe as implicit" reasoning as the original guard.
6. **Transaction + row-locking added to the three read-then-write attempt endpoints**: `PATCH /api/attempts/:id/answers`, `POST /api/attempts/:id/check`, and `POST /api/attempts/:id/submit`. Each now runs inside `db.transaction(async (txDb) => {...})`, with the attempt row read via `SELECT ... FOR UPDATE` under Postgres (a no-op clause omitted under SQLite, which has no real concurrent interleaving to guard against with a single synchronous connection). This is exactly the lost-update race Phase 4's `concurrency-test.js` proved matters for a pooled, async connection (25/25 correct with locking vs. 1/25 without) — extended here from the plan's original scope of `/check` + `/answers` to include `/submit` as well, since it shares the identical read-check-then-write shape and a double-click "Submit" is a real instance of the same race class. Flagging this scope extension explicitly rather than silently doing it.
