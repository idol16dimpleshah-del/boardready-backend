# Authentication Threat-Model Review (pre-production, requested 2026-09-24)

**Purpose:** answer, concretely and from the actual code (not from general best-practice assumptions), the questions raised alongside Phase 5's close-out — whether the current `localStorage`/bearer-token authentication mechanism is acceptable for BoardReady's chosen deployment model, or needs to change before launch. This does not implement anything; it is the evaluation the two deferred items (`HttpOnly` cookies, token revocation) were explicitly held back pending.

---

## Where is the authentication token currently stored?

Client-side, in the browser's `localStorage`, under two keys — `br_token` (the signed bearer token) and `br_user` (the user's id/name/email/role) — set on successful login/register and read back on every page load to restore the session (`public/app.js`, `saveSession()`/`loadSession()`). Every subsequent API call attaches it as `Authorization: Bearer <token>` (the `api()` helper, `public/app.js` line ~84). It is never placed in a cookie.

## How long does it live?

A fixed 7 days from issuance (`auth.js`: `TOKEN_TTL_MS = 1000 * 60 * 60 * 24 * 7`), baked into the token's own signed payload as `exp` at the moment it's signed (`sign()`). There is no refresh mechanism — a token is either still within its original 7-day window or it is dead; there is no way to extend a session's life without a fresh login. `verify()` checks `payload.exp < Date.now()` on every request and rejects an expired token with a plain `401`.

## Is it exposed to JavaScript?

Yes, completely. `localStorage` is a synchronous, fully-readable-by-any-script storage area for the origin — any JavaScript that ever executes on this origin (the app's own code, or an attacker's code if it ever got injected via XSS) can read `localStorage.getItem('br_token')` directly, in plain text, no special permission needed. This is the exact, real tradeoff already named in the Phase 5 audit and hardening report: an `HttpOnly` cookie would not be readable by any JavaScript at all, injected or not, whereas the current design's entire protection against token theft rests on *preventing script injection in the first place* (input sanitization, the CSP added in Phase 5) rather than making a successful injection harmless.

## What happens after logout?

`public/app.js`'s `logoutBtn` handler (line ~256) does exactly two things: `clearSession()` — which removes `br_token`/`br_user` from `localStorage` on *this browser only* — and shows the login screen. It does **not** call any server endpoint, and the server has no logout/revocation endpoint to call. The token itself is not invalidated in any way; it simply stops being present in this one browser's storage. If a copy of that same token exists anywhere else (a different browser it was copied to, a proxy/log that captured it, a browser extension that read it before logout), that copy remains fully valid and usable until its own 7-day expiry, completely unaffected by this logout.

## Can a stolen token remain valid?

**Yes, for up to the remainder of its 7-day window, with no way to cut it short.** Concretely, today's codebase has:
- No server-side session/token store of any kind — `verify()` (`auth.js`) checks only the HMAC signature and the `exp` timestamp, nothing else. There is nothing to consult that could say "this token was revoked."
- No password-change or password-reset route at all (grepped `server.js` in full — none exists). So even the *closest* real-world mitigation a user might expect ("someone stole my session, I'll change my password") isn't available as a feature yet. And it's worth being precise even if it were added: in a typical implementation, changing a password does not automatically invalidate already-issued tokens unless the verification path is explicitly built to check something that changes at that moment (e.g., a `tokenVersion` or `passwordChangedAt` claim compared against the user's current row) — this codebase's token payload (`{userId, role, exp}`) carries neither, so that mitigation would need to be built deliberately, not assumed to fall out of "add password change."
- No logout-everywhere / "sign out of all devices" capability, for the same underlying reason.

The practical exposure window is bounded (7 days, not indefinite), and the blast radius of one stolen token is bounded too (see below), but within that window, a stolen token is fully equivalent to the real user being logged in, from any device, indistinguishable from the legitimate session, until it naturally expires.

## How are teacher/student permissions enforced?

Every route that needs it calls `requireAuth(req, allowedRoles)` (`server.js`), which verifies the token's signature and expiry, then checks the token's own embedded `role` claim against a per-route allowlist (e.g. `['student']` for every practice/test/attempt route, `['student', 'teacher']` for `/api/chapters`). The `role` is set once, at registration, from a client-supplied value constrained to `'student'` or `'teacher'` (`users.role` has a `CHECK` constraint), baked into the token at sign-time, and cannot be altered by the client afterward without invalidating the token's signature (the whole point of HMAC-signing the payload). So role-based gating is real and correctly enforced — a student token cannot be used to call a teacher-only route, and vice versa.

**The important caveat, already flagged in the Phase 5 audit (item 9) and repeated here because it's directly relevant to "is the current mechanism acceptable":** there is currently **no teacher-facing data-access route implemented anywhere in the codebase** — no route lets a teacher account read or act on a student's data at all. So "teacher/student permission enforcement" today means only "the app correctly restricts each route to the role(s) it was built for" — a real property, verified in Phase 5's tests — not "a teacher's access to student data has been reviewed and scoped correctly," because that feature doesn't exist yet to review. When it is built, it needs its own dedicated authorization audit at that time (e.g., can a teacher see only their own assigned students, or all students — a question this codebase doesn't yet answer because the feature isn't there).

## What is the exact threat model for BoardReady?

Synthesized directly from what the codebase actually is and does, not a generic template:

- **What's being protected:** student accounts (name, email, password hash) and their practice/exam performance history (attempts, scores, per-topic accuracy, readiness trajectory) for a K10 exam-prep product. This is personal data about the student, and Class 10 students are typically minors (roughly 15–16 years old) — a real reason for above-baseline care, even though the data itself is academic-performance data, not health or financial data. **No real payment/financial data flows through this system today** — `/api/subscriptions/activate` is explicitly a demo/test stub (`server.js` line 641: "a real payment flow is out of scope here"), so there is no card data, no payment-provider token, nothing PCI-relevant to protect via this auth mechanism at this stage.
- **Likely access pattern:** students on personal phones/laptops predominantly, but plausibly also shared or public devices (school computer labs, library/cybercafe access, a shared family device) given the target demographic and Indian K10 exam-prep market context — this raises the practical relevance of "does logging out actually clear the session on that device" (yes, that part works) versus "can a token that leaked before logout still be used elsewhere" (yes, it can, as above).
- **Realistic attacker motivations against this specific app:** (a) a fellow student wanting to see or manipulate another student's scores/answers out of rivalry or curiosity — already the isolation case Phase 5 tested and confirmed rejected (item 9); (b) credential stuffing / brute force against login, given password reuse is common — mitigated by Phase 5's rate limiting; (c) an XSS-based token theft, whether from a bug in this app's own future feature work or a compromised third-party script — this is the scenario the `localStorage` design is structurally weaker against than a cookie-based one would be, and where the CSP added in Phase 5 is a real but partial mitigation (it reduces the odds of a successful script injection; it does not reduce the consequence if one succeeds anyway). There is no realistic motivation here for large-scale financial fraud or data resale, given what's actually stored.
- **A real, easily-overlooked point in the current design's favor:** bearer-token-in-header authentication is inherently immune to classic CSRF — a malicious page on another origin cannot make the victim's browser attach an `Authorization` header to a cross-site request (unlike a cookie, which the browser attaches automatically). So today's design has already "paid for" one thing that a naive migration to cookie-based sessions would have to consciously re-earn (CSRF tokens / `SameSite` cookie configuration) — worth weighing against the theft-surface tradeoff, not just treating the cookie option as strictly safer in every dimension.

## Recommendation

Given the above — a bounded 7-day exposure window (not indefinite), no financial data in scope, an already-tested and correctly-enforced student-to-student isolation boundary, a real (if partial) CSP mitigation against the main realistic attack path (XSS), and a CSRF-immunity property the current design already has "for free" — **the current mechanism is a reasonable, explainable choice for BoardReady's actual current deployment model** (a single-instance Node API serving a K10 exam-prep SPA, no payment data, no third-party embeds). It is not without a real, named gap: a stolen token cannot be revoked early, and there's no logout-everywhere capability. Whether that residual risk is acceptable to launch with, or whether it should be closed first, is a product/business call — not a purely technical one — since closing it properly (session store + revocation, or cookies + CSRF protection) is genuine architecture work, not a quick patch, and reopens exactly the frontend/backend surface Phase 5 was told explicitly to leave alone. If accepted for launch, the two lowest-effort partial mitigations worth considering independently of the bigger architecture change are: (1) shortening the token TTL from 7 days (reduces the exposure window directly, at the cost of more frequent re-logins), and (2) adding a password-change route now, even before full revocation exists, since it's a reasonable baseline expectation regardless of the token-storage question.
